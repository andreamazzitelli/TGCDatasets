# TGCDatasets

Dataset design and tooling for training two Create ML image classifiers on
macOS:

1. **TCG Identifier** — which trading card game a photographed card belongs to
   (Pokémon, Magic: The Gathering, Yu-Gi-Oh!, etc.)
2. **Grading Status** — whether the card is raw (ungraded) or encapsulated by
   a major grading company (PSA, BGS, CGC, SGC), and by which one.

These are **two independent single-label classifiers**, not one combined
model. A graded slab looks visually similar (same label shape, holder,
barcode/cert layout) no matter which TCG is inside it, so a TCG-agnostic
grading model needs far less data than trying to learn `pokemon_graded_psa`,
`mtg_graded_psa`, `yugioh_graded_psa`, ... as separate classes. At inference
time you run both models on the same photo and combine the two predictions
(e.g. "Pokémon, PSA-graded").

See `docs/taxonomy.md` for the full label list and rationale,
`docs/data_collection.md` for sourcing/licensing guidance and shot
guidelines, and `docs/createml_guide.md` for the actual Create ML workflow
(folder layout, augmentation settings, training tips).

## Quick start

```bash
# Scaffold the empty folder structure Create ML expects for both models
./scripts/scaffold_dataset.sh

# Drop images into data/tcg_identifier/train/<label>/ and
# data/grading_status/train/<label>/, then track provenance in
# data/manifest.csv (see docs/data_collection.md)
```

Open Create ML on macOS, choose the **Image Classification** template, and
point it at `data/tcg_identifier/train` (and separately at
`data/grading_status/train`) once populated.

## Repo layout

```
docs/                  Design docs: taxonomy, sourcing, Create ML workflow
scripts/               Scaffolding + manifest helper scripts
data/                  Generated by scaffold_dataset.sh (gitignored — images
                        are not committed to this repo, see below)
```

## Why images aren't committed here

Card images are either your own photographs (fine to keep locally, but large
binary churn doesn't belong in a source-controlled git repo) or sourced from
third-party databases/APIs whose terms typically restrict redistribution.
`data/` is gitignored; only the folder structure and a CSV manifest
(filename → source → license → label) are meant to be tracked, so the
dataset's *provenance* is versioned even though the pixels aren't. If you
need the images themselves under version control, use Git LFS or an external
bucket (S3/iCloud Drive) and reference it from the manifest — this repo
doesn't set that up for you since it depends on how much data you end up
with.
